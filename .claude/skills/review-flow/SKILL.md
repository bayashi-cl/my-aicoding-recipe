# レビューとフィードバックのフロー

## 多段レビューモデル

PR は以下の順で確認される。早い段階で防げるものは早い段階で防ぐ。

```
PR作成
  ↓
[Layer 1] CI: 型チェック、lint、ユニットテスト
  ↓
[Layer 2] AI自動レビュー: /review および必要に応じて /ultrareview
  ↓
[Layer 3] 人間レビュー: 上記の指摘を踏まえて最終判断
  ↓
マージ
```

## PR提出前にやること（AI自身がやる）

1. 差分を自分で読み返す（`git diff main...HEAD`）
2. スコープから外れた変更がないか確認
3. 型チェック・lint・テストをローカル実行
4. `/review` 相当のセルフレビューを実施
5. 重要度の高い変更（DB スキーマ、認証、外部 API 連携等）には `/ultrareview` を提案

## レビュー指摘への対応

- 指摘は **採用する / 採用しない / 別 Issue に切る** のいずれかを明示する。沈黙させない。
- 採用しない場合は、なぜ採用しないかをコメントで返す。
- 指摘ごとに別コミットで対応する（1指摘 = 1コミット）と差分が追いやすい。
- 大幅修正が必要な指摘は、その PR を一旦 close し、新規 PR を立てるのも選択肢。

## フィードバックの昇格ルール

レビューで **繰り返し** 出る指摘は、以下のいずれかに昇格させる。同じ指摘を3回受けないことを目標にする。

| 指摘の性質 | 昇格先 |
|------------|--------|
| 機械的に検出できる（型・lint・テスト） | lint ルール、型定義、テストケース |
| 判断基準・スタイル全般 | `.claude/skills/coding-style/SKILL.md` |
| Git・PR 運用に関するもの | `.claude/skills/git-workflow/SKILL.md` |
| プロジェクト固有の経緯・判断 | `.claude/memory/` に memory として追加 |
| プロジェクト全体のスコープ・方針 | `docs/requirements.md` または `docs/design.md` を更新 |

## ジャーナル

このリポジトリの **本来の成果物は「AI開発の型」** であり、その記録がジャーナル。

### 書くタイミング

- マイルストーン完了時
- ワークフロー上の発見・つまずきがあったとき
- ハンドオフ（ローカル ↔ Cloud Agent）を試したとき

### 書く場所

`docs/journal/YYYY-MM-DD-<topic>.md`

### 書く内容（テンプレ）

```markdown
# YYYY-MM-DD <topic>

## 何をやったか
<事実を簡潔に>

## うまくいったこと
<どこが効率的だったか。なぜ効いたか>

## つまずいたこと
<何が遅延・失敗の原因だったか>

## 次に活かすこと
<次セッション以降で変える方針。スキルやmemoryへの昇格候補>
```

### 注意

- ジャーナルは **長く書かない**（1ファイル 100行を上限の目安に）。
- コードでわかる「何を作ったか」は書かない。「**プロセスについて何を学んだか**」を書く。
